# CI overview

All workflows only run on `main` (and by hand). Everything here is **untested** until the first run on GitHub; locally only the YAML was parsed.

## Per repository

| Repository | Workflow | Build | Runner |
|---|---|---|---|
| raccoon-cli | `build-release.yml` | `python3 build.py --version <n>` (job `build-and-release`), then PyPI and the release; `test` as before; `ci-image.yml` follows the Dockerfile | `ubuntu-latest` |
| raccoon-transport | `ci.yml` | `build-and-test` as before (C++, Dart, Python); `python3 build.py --version <n>` in `build-and-release`, then PyPI and notifying the components | `ubuntu-latest` |
| botui | `build-release.yml` | `python3 build.py --version <n>`, artifact `botui-deb`, release, notify raccoon-image | `ubuntu-latest` |
| stm32-data-reader | `build-release.yml` | `python3 build.py --version <n> --test` **natively** on an ARM runner, artifact `stm32-data-reader-deb`, release with that `.deb`, notify raccoon-image | `ubuntu-24.04-arm` |
| raccoon-lib | `ci.yml` | **as before**: cibuildwheel for the four release wheels (Linux x86_64 and aarch64, macOS, Windows), stub wheel from `scripts/build-stubs.sh` in `publish-pypi`, `publish-library`. `build.py` builds no release file. The job `test` runs `python3 build.py --test --python-tests` natively (C++ tests and the fast Python tests; the simulator tests not yet, issue #109) and does not gate the release | matrix; `test` on `ubuntu-24.04-arm` |

Why raccoon-lib is different: PyPI accepts only manylinux tags for Linux, `build.py` builds in a Debian 13 image (`linux_aarch64`), and Windows and macOS wheels cannot be built in a Linux Docker image. The job `build` (tarball with `install.py`, switched off with `if: false`) is removed. The job `test` was switched off too and used `build.sh` and `.github/docker/Dockerfile`; it now runs `build.py`.

## The `release` switch

Every one of these workflows has a manual input `release` (default on). Untick it under Actions, "Run workflow": everything is built with the next release number as version and the results are workflow artifacts, but there is no tag, no GitHub release, no PyPI upload, no documentation trigger and no notification. It also works on a branch. A push to `main` always releases.

## What to check on the first runs

1. **The switch, in every repository:** run by hand with `release` unticked. The build must be green and nothing may be published or notified. Do this first, a mistake here would publish something.
2. A normal run on `main` with `release` on: it releases as before.
3. **stm32-data-reader:** the job runs `--test` natively on ARM for the first time, including `reader_contract_smoke`. The artifact `stm32-data-reader-deb` must exist.
4. **raccoon-lib:** the job `test` is green (`SharedTransportTest` can fail now and then, see the status page); the four wheels build as before and `publish-pypi` writes the stub wheel with `build-stubs.sh`. Both PyPI packages must have the same number.
5. **botui:** the artifact `botui-deb` exists.
6. **raccoon-cli and raccoon-transport:** green build, release only with the switch on.
7. Install the artifacts of a test run with `deploy.py` (reader `.deb`, botui `.deb`) and check that a CI build behaves like a local one.
8. Merge order: raccoon-image before or together with raccoon-cli, and the reader, raccoon-cli and raccoon-image together (see the status page).
